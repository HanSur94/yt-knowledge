# Stage 5 — Initial Zoom Out Review

**Document:** docs/designs/yt-knowledge.md (366 lines)
**Mode:** REVIEW · **Standard:** Zoom Out · **Date:** 2026-10-31

## Verdict

**Fail.** The design is unusually well grounded — every load-bearing choice traces to a measured fact, the ingest boundary is correct (`collector pushes, the server receives`), the state column honestly replaces a queue, and the alternatives section rejects the right things for the right reasons. But it fails on one thing that cannot be patched at the edges: the only search index covers `title, channel, headline, bullets`, while the goal, CUJ 3 and the acceptance test all require finding a phrase that lives in the transcript. That is the app's entire reason to exist ("find the thing I watched two months ago"), and the schema as drawn cannot answer it. Around that blocker sit several smaller internal contradictions — a read-only MCP server carrying a write tool, a backfill estimate that measures only one of four network stages, an unstated mechanism for reaching SQLite from a stdio process — none fatal alone, all cheap to fix in the doc now and expensive to discover at implementation.

## Findings

1. **[BLOCKER]** The sole FTS index is `videos_fts FTS5 over title, channel, headline, bullets` (line 153), so the goal to "Answer a phrase-level question in under a second over 4,000 videos" (line 38), CUJ 3's "scrolled to the matching transcript line" (line 94) and the acceptance test "a phrase known to be in a specific video is found by searching the library" (lines 361-362) cannot pass, because nothing indexes the `segments` table where the transcript text actually is.
2. **[MAJOR]** "the measured ceiling is about 55 videos a minute and the run is expected to take about 77 minutes" (line 87) applies a transcript-only rate — 1.09 s per video — to a pipeline that also does a `yt-dlp --dump-json` metadata call, a thumbnail GET, a SponsorBlock call and one LLM summary call per video (lines 117-119, 292-310), and the added "0.5 s between requests" (line 239) alone would drop 4,253 videos to roughly 37/min, so the end-to-end estimate is wrong by at least an order of magnitude.
3. **[MAJOR]** The document never says where `mcp_server.py` runs or how a "MCP stdio server" with a "Read-only SQLite connection opened per request" (lines 325-326) reaches a file that lives in the NAS container, while CUJ 4 assumes it is "registered in Claude or Codex against the same SQLite file" (lines 99-100) — if that means a mounted network share, "SQLite with WAL" (line 239) is not supported over it.
4. **[MAJOR]** `run_digest()` is listed both in the API surface (line 172) and among the MCP tools (line 328), yet `mcp_server.py` is specified as a read-only connection "No write tool" (lines 326-329), leaving the one non-read tool with no defined path to trigger the job.
5. **[MAJOR]** "GET /export/md write markdown tree into the export volume" (line 170) is a side-effecting GET that carries no token — the token dependency is only on `/import` and `/digest/run` (line 316) — which breaks the stated invariant that the service "exposes no admin action without the token" (lines 235-236).
6. **[MAJOR]** The state machine is enumerated as "`pending|fetched|ready|failed|no_caption`" (lines 133-134) but the filters section then relies on "`state='archived'` retires them so a re-import does not resurrect noise" (lines 158-159), a sixth value that is absent from the contract and whose re-import behaviour (does a new qualifying watch leave an archived row archived?) is left undefined.
7. **[MAJOR]** "a single English sentence is stored alongside for cross-language search" (lines 181-182) has no column in the `summaries` table — `video_id, lang, headline, bullets_json, tags_json, model, created_at` (line 152) — so the cross-language search surface has nowhere to be written or indexed.
8. **[MAJOR]** "the same endpoint serves one user and ten" (lines 129-131) is asserted as the justification for the push API, but there is no user key and one SQLite file (line 41), and the predecessor brief already established that multi-user costs "One SQLite file per user, a push endpoint that takes a user key" (concepts_brief.md, line 190) — the boundary is justified by lines 54-55 alone and needs no tenancy claim.
9. **[NIT]** The weekly digest appears as `/digest`, `/digest/run`, `digest.html`, `digest()` and `run_digest` (lines 168-169, 309, 333, 328) yet no Goal names it, so the one feature the brief calls "the one that earns the app being opened" (concepts_brief.md, line 330) is carried as unstated scope.
10. **[NIT]** The architecture diagram is titled "NAS container (one process)" (line 115) while the same diagram annotates `mcp_server.py` as a "(separate process, read-only connection)" (lines 123-124) — one of the two labels is wrong and the MCP placement is the load-bearing one.
11. **[NIT]** `videos_fts` indexes `headline, bullets` which live in a different table (lines 152-154) and `db.py` lists only `init()` and four helpers (lines 262-266), so nothing in the design says how the FTS rows stay in sync when a summary is regenerated.
